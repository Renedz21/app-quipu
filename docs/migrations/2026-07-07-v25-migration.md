# v2.5 migration runbook

## Order of operations

Run these mutations in this exact order against a deployment. Each is idempotent; safe to re-run.

1. `migrations:backfillProfilesV25`
   - Sets `incomeModel` on every profile.
   - Clears `payFrequency` and `paydays` on profiles migrated to `variable`.
2. `migrations:backfillCommitmentsV25`
   - Sets `dueDay` on every commitment using the profile's `paydays`.
   - Trade-off: `every_payday` commitments lose to first payday only. Show users a banner in `/settings` asking them to verify.

> **Note:** `backfillCyclesV25` and `backfillIncomeEventsV25` were part of Phase 2 but were removed when the v2.0 fields were dropped in Phase 3 (Task 26). The cycle snapshot is now maintained atomically by `createIncomeEvent`, and `adHocIncomes` rows were copied to `incomeEvents` during the Phase 2 run of `backfillIncomeEventsV25`. If you still have `adHocIncomes` data in a deployment, run the historical version of the migration (see git history) **before** deploying the Phase 3 narrow.

## Pre-flight

- Snapshot the database (or at least the affected tables) before running.
- Confirm all mutations return `0` for the `*Updated` field when run a second time (idempotency check).

## Post-flight

- `count(profiles where incomeModel = undefined) === 0`
- `count(fixedCommitments where dueDay = undefined) === 0`
- `count(financialCycles where totalIncomeReceived is null AND status = "active") === 0` (active cycles should always have a total)
